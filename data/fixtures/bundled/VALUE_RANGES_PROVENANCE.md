## Derivation rules

- A range's name takes the most specific thing OFL states: `comment`, else the
  wheel slot, else `shutterEffect`/`effectName`, else `colors` with the
  capability type, else the type alone. Speed, angle and intensity spans are
  appended as `start->end`; `randomTiming` appends `(random)`. Where a
  capability carries both an effect and a comment the effect leads and the
  comment trails in parentheses.
- Adjacent capabilities that derive the *same* name are merged into one range.
  This is lossless: each part already asserted that meaning.
- Names are folded to ASCII, matching the rest of the corpus.
- Fine channels never receive ranges, matching `gdtf_parser`.
- Channels OFL models as one continuous capability (pan, dimmer, a bare zoom)
  are skipped: there are no slots to name.

If you audit a range against an OFL *web page* rather than its JSON, expect the
page to have more rows than we do where consecutive capabilities share a name
(we merged them), and fewer where a capability is pure "no function" (the page
hides those, the API returns them and we keep them, so the byte space stays
fully accounted for).
